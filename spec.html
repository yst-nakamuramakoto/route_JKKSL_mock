MUSUBOなびゲート routesupport

営業支援ルート最適化アプリ。Google Workspace Frontline 導入を前提に、社員のGoogleカレンダーを起点として、営業訪問・既存利用者モニタリングの計画から実行までを支援する。

1目的

Google Workspace Frontline 導入を前提に、社員のGoogleカレンダーを起点として、営業訪問・既存利用者モニタリングの計画から実行までを支援する。

2ブランディング／UI構成方針

  • アプリ名：「MUSUBOなびゲート」（英語表記：routesupport）。サイドメニュー上部のブランド表示、ブラウザタブタイトルに使用。
  • イメージカラー：ブランドカラーは「むすぼなグリーン」。本モックでは仮で #4CAF50（主要アクション・マスコット用）と #2E7D32（サイドメニュー・見出し等の背景・テキスト用の濃いグリーン）を採用。正式なブランドカラーコードが確定したら差し替える。
  • マスコット（MuK）：ブランドのマスコット（緑色のキャラクター、画像ファイル MuK.jpg）を要所に配置。本モックでは「サイドメニュー上部のブランド表示」「ホームのFABメインボタン（マスコット画像化）」「滞在アラートの強制ポップアップ通知」に採用。
  • UIトーン：カードや帯を太い色ボーダーで装飾する手法（いわゆる「AIツールっぽい」見た目）を避け、Googleカレンダーに近い「白背景＋薄いグレー罫線＋軽い影」のトーンで統一。色は状態表示（優先度・当日・ラベル分類など）にのみ使用し、装飾目的では使わない方針とする。全画面に同トーンを展開済み。

サイドメニュー（ドロワー式）

  • 画面左上のハンバーガーボタン（☰）でスライドイン表示し、画面外タップで閉じるドロワー形式。常時表示ではなく必要時のみ呼び出し、コンテンツ表示領域を最大化する。
  • メニュー項目と順序（固定）：🏠 ホーム／✅ タスク／🗺️ ルート提案／🅿️ 駐車場リスト／🤖 AI提案／⏰ 滞在アラート
  • AIアシスタントはサイドメニューには含めず、FABのサブボタンから呼び出す。
  • Google連携ステータス表示：ブランド表示の下に「Google連携済み」バッジ（緑ドット＋テキスト）を配置。本モックでは表示のみのダミーで、実際の認証・API接続は行わない。実データ連携フェーズでは、実際のGoogle OAuthログインボタンや個別API（Calendar／Tasks）ごとの接続状態表示に置き換える想定。

トップバー

  • 画面上部の緑帯（ブランドカラー）。左端にハンバーガーボタン（☰）、中央に現在画面のタイトルを表示。
  • ホームに戻るボタン：右端に配置。アイコンはカーブ矢印（↩️）。ホーム画面表示中は非表示、それ以外の画面ではタップでホームに戻る。

FAB（フローティングアクションボタン／MuKボタン）

  • ホーム画面のみに表示する、直径80pxのマスコット画像ボタン。タップでサブボタンが展開：「🎙️ AIと話す」「🤖 AI提案を追加」「✅ タスクを追加」「予定を追加」の4択。
  • ドラッグ移動対応：ユーザーが親指の届く位置に自由に移動できる（タッチ／マウス両対応）。ドラッグと短タップを判別し、移動距離が小さい場合はタップとしてサブボタンを展開する。

モバイル対応方針

  • viewport メタタグ（width=device-width, initial-scale=1）を設定し、スマホ実寸で表示する。
  • タッチ領域は Apple Human Interface Guidelines の 44px 基準を遵守。
  • フォントは最小13px、主要テキストは15px以上で可読性を確保。

3対象機能（6画面＋AIアシスタント）

各画面の目的・入出力データ・画面要素を定義する。

①ホーム（スケジューラー：日／週／月）
目的
Googleカレンダーの予定をベースに、当日・週・月単位でスケジュールとタスクを一覧・登録・削除できる起点画面。同僚（同一ワークスペース内の他メンバー）の予定も重ねて確認できる。
入力データ
Googleカレンダーの予定・空き時間（Calendar API）、アプリ内タスク（期限・完了状態）、閲覧対象メンバーのカレンダー（同一Google Workspaceドメイン内）。
出力
日／週／月ごとの予定＋タスク表示。FAB経由の予定追加・タスク追加・削除（確認ダイアログ付き）。

画面要素

  • 日・週・月の切替タブ
  • メンバー選択チップ：タブ下に横並びで表示。自分の予定は常に表示されるためチップ化はせず、同僚のみチップ表示。タップで表示ON/OFFを切り替え可能。選択中のメンバーが日／週／月表示すべてに反映される。
  • メンバーの追加（「＋追加」ボタン）：チップ列の末尾に配置。タップするとGoogleアカウント（メールアドレス）をキーにした候補一覧（ダミーの固定リスト）がポップアップで開き、チェックボックスで選択→「選択を確定」で表示メンバーに追加される。
  • メンバーの削除（チップの「×」）：各同僚チップの右側に「×」を配置。タップ（削除確認あり）するとそのメンバーを表示から完全に削除し、「＋追加」の候補一覧に戻る。
  • 日表示：選択中メンバーごとにセクションを分け、それぞれの時刻＋件名のタイムラインを縦に並べて表示（複数人分を縦スクロールで確認）。
  • 週表示：日表示と同様にメンバーごとにセクションを分け、各セクション内に曜日ごとの予定を一覧表示。当日は緑色ヘッダーでハイライト。
  • 月表示：日付セル＋メンバーごとに色分けしたドット表示（自分＝グリーン、同僚＝赤・黒など）で、誰の予定がある日かを一目で確認できる。
  • 今日のタスクリスト（チェックボックス・削除ボタン）／右下FAB（MuKボタン）

予定の色分け・編集権限

予定名の左のドット色でメンバーを識別（メンバー選択チップと同じ色）。自分の予定はタップで内容を編集可能、同僚の予定はタップすると「閲覧のみ」の詳細ポップアップが開き、編集・削除はできない。

日付表示・ナビゲーション

  • 画面上部に日付バッジを常時表示（日：yyyy/mm/dd（曜日）、週：yyyy/mm/dd～yyyy/mm/dd、月：yyyy/mm）。
  • 週・月表示では日付バッジ両側に「‹ ›」ボタンを表示し、前後の週／月へ移動できる。
  • 日付バッジのタップでカレンダー表示：日／週／月いずれの表示中でも、上部の日付バッジをタップするとカレンダー（タスク期限選択と同じポップオーバー部品）が開き、任意の日付を選択できる。選択すると日表示に切り替わり、その日のスケジュールを確認できる（過去・未来どちらも選択可）。
  • 空き時間からAI提案への遷移：タイムライン上の空き時間カードに「🤖 AI提案を見る」ボタンを設置し、AI提案画面へ直接遷移できる（自分の空き時間のみ表示・対象）。
  • 月表示から日表示への遷移：月表示の日付セルをタップすると、その日付で日表示に切り替わる。
  • 日表示の制約（ダミーデータ）：本モックではメンバーごと・日ごとの実データを保持していないため、日表示の予定内容は「曜日」に基づくダミーデータを流用して表示する（例：火曜日を選択すると、週表示の火曜日と同じ内容が表示される）。実際の日付固有の予定ではない点に注意（実データ連携時の対応は「7. 今後の検討事項」参照）。
  • 予定タップで詳細編集：日表示・週表示の予定（空き時間を除く）をタップすると編集ポップアップが開き、タイトル・時間（開始／終了）・場所・予定内容（いずれもダミーデータ）を確認・編集できる。「保存する」でタイムライン表示に即時反映、「キャンセル」で破棄。表示上の反映のみで、Googleカレンダーへの実書き込みは行わない。
  • 予定追加モーダルの入力項目：タイトル／日付／時間帯（ロールピッカー）／場所に加えて、「予定内容」の複数行テキストボックスを設置。
  • 予定・タスクの「メンバーに共有」機能：予定の登録モーダル・予定編集ポップアップ（自分の予定のみ）・タスクの登録モーダル・タスク編集ポップアップに「共有」欄を設置。「＋メンバーに共有」ボタンからメンバー追加と同じ候補ピッカー（自分を除く）を開き、複数選択して共有先チップとして表示できる。共有操作はUI上の記録のみで、共有先ユーザーの画面に実際に反映される連携は行わない（実データ連携時はGoogleカレンダーの「ゲストを追加」やタスクの共有権限設定に相当する処理が必要）。
  • タスクタップで詳細編集：ホーム・タスク画面いずれのタスク（チェックボックス・削除ボタンを除く）をタップすると編集ポップアップが開き、内容・期限（開始日／終了日）を編集できる。ラベルはタスク画面のようにラベルが設定されている場合のみ編集欄を表示。
②AI提案
目的
指定した日の空き時間に対し、訪問すべき先（新規営業／既存利用者モニタリング）をAIが提案する。当日に限らず任意の日を指定可能。
入力データ
指定日のGoogleカレンダーの空き時間、基幹貸与システムの顧客データ（利用状況・前回訪問日・優先度）。
出力
指定日における複数の空き時間帯ごとに、複数件の訪問先提案（訪問理由・優先度・所要時間）。採用するとホームの予定として登録。
  • 日付指定：前日／翌日送りボタン＋ミニカレンダー（タップで展開）
  • 時間帯ごとの提案カード群：顧客名・理由・優先度・所要時間・採用／却下ボタン
  • タグ表示：優先度（高/中/低）、対象種別（個人/新規営業/モニタリング）。対象顧客は法人・個人の両方を含み、個人は「個人」タグ付きで氏名表示。

将来構想：自社BIツール連携による高精度AI提案

自社BIツールと連携し、販売・利用実績データをAIが解析した上で訪問先・優先度を提案。課題分析（利用実績の変動推移）とフロントトーク案（切り出し方・提案トーク）まで提案内容に含める。本モックではサンプルカード（Coming soon表示）のみ掲載。実データ連携はフェーズ3以降。

③タスク（一覧＋ガントチャート）
目的
Googleカレンダーにはない「やることリスト」を種別ごとに分類・管理する。
登録項目
タスク名、開始日、終了日（期間指定）、ラベル、共有メンバー（任意・「＋メンバーに共有」で選択）。

ラベル分類

  • 🔵 利用者：個人利用者への連絡・報告・モニタリングフォロー
  • 🟢 紹介先：法人・紹介先企業への営業フォロー・見積り・契約手続き
  • 🟠 市区町村：行政機関（市区町村・ケアマネ等）への書類送付・会議対応
  • ⚪ 事務処理：実績入力・書類作成・社内処理等の内部業務
  • ラベルフィルターバー：タスク画面上部に「すべて／利用者／紹介先／市区町村／事務処理」のフィルターボタンを常時表示。タップで即時絞り込み。
  • ガントチャート：タスク画面右上の「📊 ガントチャート」ボタンで遷移。2週間スパンの横棒チャートで各タスクの期間を可視化。本日ラインを緑色で強調表示。完了タスクはグレーバーで識別。
④ルート提案（駐車場提案をデフォルト統合）
目的
複数訪問先が決まった際、移動効率の良い巡回順をAIが提案する。各訪問先に最寄りのコインパーキングをデフォルトで併記し、駐車場探しの手間を削減。
入力データ
訪問先リスト（緯度経度）、出発地、各訪問の希望時間帯、訪問先周辺の駐車場満空情報。
出力
最適化された訪問順序、地図上のルート表示、移動時間・距離の合計、各訪問先の推奨駐車場（空車数・距離）。
  • ルートは「提案」であることの明示：「このルートを採用する」または「別ルートを再提案」を選択できる。
  • 各訪問先カードに「駐車場までナビ開始」ボタンを配置。駐車場座標を目的地として外部ナビへ連携する（駐車場不要な場合は「ナビ開始」ボタン）。
  • 満車時の挙動：最寄り駐車場が満車の場合、「満車のため他の駐車場を選ぶ」リンクを表示し、⑤駐車場リスト画面の該当訪問先へ遷移。
  • モックでの地図表現：Googleマップ埋め込み＋キャプション。実ルート線描画はGoogle Maps Routes APIによる本実装時に対応。
⑤駐車場リスト（単独ビュー・訪問先別）
目的
ルート提案とは別に、特定の訪問先周辺の駐車場を単独で確認・比較する。
  • 訪問先セレクター：「🏢 訪問先を選択」のドロップダウンで切り替え。見出しに「（訪問先）への訪問用 近隣パーキング」と常時明示。
  • 駐車場一覧（空車／満車・距離・料金目安）、ルートへの追加ボタン。④から満車リンクで遷移した場合は該当訪問先が自動選択された状態で表示。
⑥滞在アラート
目的
訪問先での滞在が長引いた場合に通知し、スケジュール遅延を防ぐ。「連絡が入ってきた」という自然な退席の空気をつくる着信風UIを採用。
カウント開始
GPSが訪問先のジオフェンスへの進入を検知した瞬間から滞在時間をカウント開始（予定時刻ベースではなく実到着ベース）。

出力（通常画面）：残り時間カウントダウン（残り10分で黄色警告、超過で赤警告）、通知ログ。出力（実際の通知発報時）：「5. 滞在アラートの強制通知仕様」に従う。

⑦AIアシスタント（音声入力＋チャットボット）
目的
運転中・フリック入力が困難な状況でも、マイクへの話しかけだけで主要操作を完結できるようにする。
呼び出し方
FABのサブボタン「🎙️ AIと話す」からチャット画面を呼び出す。テキスト・音声の両入力に対応。
  • 音声入力：Web Speech API でマイク音声をテキスト変換し送信（Chrome/Edge対応、Safariは一部制限あり）。録音中はマイクボタンが赤く点滅。
  • テキスト入力：チャット形式でメッセージを入力・送信（Enterキーまたは送信ボタン）。

主な対話シナリオ（5種）

  1. スケジュール登録：「明日14時にA商事の訪問を追加して」→ カレンダー登録の確認返答
  2. AI提案の採用：「13時の提案を採用して」→ AI提案画面へ自動遷移
  3. ルート再設定：「山田さんのところに行きたい」→ ルート提案画面へ自動遷移
  4. タスク追加：「B工業の見積書送付をタスクに追加して」→ タスク追加の確認返答
  5. スケジュール確認：「今日のスケジュールを教えて」→ 本日の予定一覧を返答

モックでの実装：ルールベースの会話パターンで5シナリオをデモ動作。想定外入力には「もう少し詳しく教えてください」と返すフォールバックあり。

本実装での技術方針

  • LLMと接続し、自然言語の意図解析（インテント判定）を行う（採用方針は「6. システム構成」参照）。
  • Calendar API・ルート提案ロジック・タスクDBをFunction Callingで呼び出す。
  • 音声はブラウザ内でテキスト変換後にLLMへ送信（音声データ自体は外部送信しない）。

5滞在アラートの強制通知仕様

通常のメニュー画面（⑥滞在アラート）はカウントダウン確認用UIだが、実際のアラート発報時は他の画面を表示中でも以下3点を同時に実行する。

  1. 着信風ポップアップ：全画面に「📞 着信中」スタイルの強制ポップアップを最前面表示。グリーン系グラデーション背景＋電話ベルアイコンが揺れるアニメーション。「応答ボタン（退出）」「確認ボタン（続行）」の2択で自然な退席演出を実現。確認するまで他操作をブロック。
  2. 着信音：電話の着信リズム（880Hz/660Hzの交互パターン）をWeb Audio APIで再生。
  3. 端末バイブレーション：navigator.vibrate([500,200,500,200,500,200,500]) で着信パターンのバイブレーションを作動（本実装ではプッシュ通知＋端末標準の通知音・バイブレーションAPIを利用）。

6システム構成・API方針の決定事項 決定

本実装に向けて確定した方針。詳細な契約条件・費用等は別途確認が必要だが、採用する仕組み自体は下記で決定とする。

インフラ基盤

Cloudflareで一本化：Workers（API・秘匿キー管理層）＋D1（タスク共有関係・訪問履歴・通知ログ等アプリ固有データの保存）＋KV（ディレクトリ情報等のキャッシュ）＋Queues（プッシュ通知の非同期配信）で構成する。Amazon Bedrock・Google各API・社内システムAPIの呼び出しはすべてWorkersからサーバーサイドで行い、APIキーをクライアントに露出させない。将来リレーショナルなデータ構造がより複雑になった場合は、Postgres（Supabase等）への部分移行も可能な構成としておく。

駐車場データ取得方針

タイムズ・三井のリパークへの個別提携交渉は行わず、集約系API（ナビタイムジャパンの駐車場検索API、ZENRIN Maps API／いつもNAVI API）を優先して採用する。契約条件・費用は別途確認。

滞在アラートのプッシュ通知

Amazon Bedrock（自社むすぼなAI）を優先採用。API発行が難しい場合はAnthropic Claude APIをフォールバックとする。
